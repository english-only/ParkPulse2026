# Park Pulse — Full Project Audit

**Date:** 2026-10-05
**Scope:** `artifacts/park-pulse` (frontend), `artifacts/api-server`, monorepo tooling
**Method:** live browser inspection of the running dev server (`localhost:5173/explore`, viewport 1440×900, both themes), computed-style and WCAG-contrast measurement in-page, `PerformanceObserver` long-task sampling, production bundle analysis, source review, ArcGIS REST probing of real council data sources, plus the three connected MCPs (context7, radix-ui, shadcn).

**Caveat on method:** screenshot capture was unavailable in this webview (frames were never composited), so all visual findings are derived from computed styles, the accessibility tree, and the stylesheet rather than from pixels. Scroll-FPS sampling returned ~2 fps, which is a headless-throttling artefact, not a defect — I discarded it and used long-task timing instead, which is reliable. Numbers below are measured, not estimated.

---

## 1. Headline verdict

The runtime is in genuinely good shape. Load is 174 ms, the heap sits at 15 MB, there are **zero long tasks** across map zoom and marker reconciliation, and the DOM is 3,364 nodes. The data layer is the strongest part of the codebase — real UTF-8 byte accounting, per-entry ceilings, two-attempt quota eviction, 7-day TTL.

The problems are almost entirely in three places:

1. **A keyboard trap in the filter panel** (all 12 filters are mouse-only) — this is the single most serious defect in the app.
2. **A colour-token leak** that keeps light-mode chips in dark themes, producing 109 measured WCAG AA failures.
3. **A data provenance lie** — 1,605 features labelled "Blacktown City Council" are in fact OpenStreetMap extracts.

## 2. Severity-ranked findings

### S1 — Significant

#### S1.1 All 12 filter checkboxes are unreachable by keyboard
`index.css` applies `.pp-filter-checkbox input { display: none }`. `display: none` removes the element from the accessibility tree *and* from the tab order — unlike `opacity: 0` or a visually-hidden clip. Verified in-page:

```
checkboxInputs: 12   checkboxDisplayNone: 12
cb.focus() → focused: false, activeElement stays BUTTON.pp-filters-toggle
```

Clicking the wrapping `<label>` does toggle the box (`togglesByLabelClick: true`), so the app works perfectly for a mouse user and is completely unusable for a keyboard user. This is a WCAG 2.1 SC 2.1.1 (Keyboard) failure, and it gates the app's primary feature — the overlay layers.

**Fix:** replace `display: none` with a proper visually-hidden pattern (clip-path/1px technique), keeping `appearance: none` for styling.

#### S1.2 109 WCAG AA contrast failures in the dark theme
`.pp-size-*` badges hardcode light backgrounds and are never overridden per theme (`index.css:553-557`):

```css
.pp-size-tiny{background:#f0f0f0;color:#888}   /* 3.11:1 — needs 4.5 */
.pp-size-small{background:#e8f4fd;color:#2980b9}/* 3.85:1 */
.pp-size-med{background:#eafbf1;color:#27ae60}  /* 2.68:1 */
.pp-size-large{background:#fdf4e7;color:#e67e22} /* 2.61:1 */
```

Measured failure counts by colour pair in the dark theme:

| Colour on | Background | Count | Ratio |
|---|---|---|---|
| `rgb(136,136,136)` | `rgb(240,240,240)` | 62 | 3.11 |
| `rgb(41,128,185)` | `rgb(232,244,253)` | 28 | 3.85 |
| `rgb(46,160,67)` | `rgb(15,47,26)` | 8 | 4.32 |
| `rgb(230,126,34)` | `rgb(253,244,231)` | 5 | 2.61 |
| `rgb(39,174,96)` | `rgb(234,251,241)` | 5 | 2.68 |
| `rgb(255,255,255)` | `rgb(63,185,80)` | 1 | 2.54 |

The same light-only problem affects `.pp-park-type-badge` variants (`.iconic`, `.sportsfield`, `.neighbourhood`, `.pocket`) and `.pp-facility-badge-dog` (`#f0fdf4` on `#166534`). The active sort chip (white on `#3fb950`, 2.54:1) also fails.

The existing e2e contrast spec passes because it evidently only samples a narrow set of selectors — these badge classes are not covered. That is itself a finding: **the contrast test has a coverage gap that hides 109 real failures.**

#### S1.3 `blacktown.geojson` is OpenStreetMap data mislabelled as council data
`public/data/meta.json` declares `"blacktown": "Blacktown City Council"`. Every one of the 1,605 features carries an OSM `@id` (`way/4904026`) and OSM-shaped properties (`@geometry: "center"`):

```
features with OSM @id: 1605 / 1605
```

The bbox is `lon 150.778–150.983, lat -33.851–-33.620` (≈19 × 26 km). Cumberland's `Central Gardens Nature Reserve` is in that file — so the layer spans Blacktown, Cumberland and Parramatta while claiming to be one LGA. Two consequences: the attribution is incorrect (OSM requires ODbL attribution, which is absent), and the layer name misleads anyone reasoning about jurisdiction.

#### S1.4 No route-level code splitting; one 524 kB eager chunk
`App.tsx` statically imports all four pages and `vite.config.ts` has no `rollupOptions`/`manualChunks`. The production build emits a single JS file (524 kB raw / **157.3 kB gzip**) plus 152 kB CSS (28.8 kB gzip). A visitor landing on `/` downloads Leaflet, markercluster, the entire Explore page, and its 1.1 MB parks GeoJSON even though the map is not on screen.

Genuinely good news: I verified the 44 unused shadcn components (recharts, cmdk, vaul, embla, react-day-picker, framer-motion) are **fully tree-shaken** — none appear in the built bundle. So this is maintenance debt, not a payload problem.

#### S1.5 504 touch targets under 24×24 px
Measured across focusable elements: the card save / locate / copy-link buttons are 20×20, the "↺ refresh" control is 49×18, and the "?" help button is 22×22. WCAG 2.2 SC 2.5.8 (Target Size, Minimum, 24×24) is a Level AA criterion. These are dense-list affordances so this is a real but lower-severity issue than S1.1.

### S2 — Moderate

#### S2.1 3,456 elements use `transition: all`
Counted in-page. This forces the compositor to watch every animatable property on every node, including the 418 Leaflet markers and the long result list. The stylesheet's own idiom should be `transition: <specific properties>` — the codebase already does this correctly in several places (`.pp-scroll-top-btn` uses `opacity, transform`), so this is inconsistency rather than ignorance.

#### S2.2 100 elements pinned with `will-change`
`will-change` is being applied broadly and permanently. Per spec it should be reserved for elements about to animate and removed afterwards; permanently applied it consumes GPU memory and can degrade exactly the low-end devices this app targets.

#### S2.3 Theme choice is not actually persisted
`useTheme.ts` writes to `localStorage` under `parkpulse_theme`. Measured after two explicit theme clicks: `localStorage.getItem('parkpulse_theme')` → `null`, and `data-theme` stayed `dark`. The click handler dispatches a custom event, so the theme *appears* to change visually, but the write is not landing. A user who picks Sunset gets Modern Green again on reload. Worth noting the code's `try/catch` around `setItem` swallows the failure with only a `console.warn`.

#### S2.4 Modal has `aria-labelledby` but no description
Verified on the live dialog: `role="dialog"`, `aria-labelledby="modal-title"` (correct, per the radix-ui Dialog primitive docs I pulled), but `aria-describedby` is `null` and `aria-modal` is not set on the element (Radix handles modality via its focus trap, so this is acceptable, though explicit is better). A `Dialog.Description` — even visually hidden — would give screen-reader users the park's key facts on open.

#### S2.5 1,258 kB of localStorage cache with no user-visible size readout
`dataCache` tracks usage via `cacheUsageBytes()` but the UI shows only a "Cached data" label. Users on quota-limited browsers get a silent performance cliff. There is already a `quota` `CacheNotice` kind wired to listeners — surfacing it is a small change.

#### S2.6 `Explore.tsx` is 2,341 lines with 28 `useEffect`s and 35 `useState`s
This single file owns map init, marker reconciliation, six data loaders, filtering, sorting, geocoding, theming, and all the results-list rendering. It is the largest file in the app by a wide margin (next is `ui/sidebar.tsx` at 727). Every future facility dataset makes it worse. Note the codebase is otherwise clean — zero `eslint-disable`, zero `@ts-ignore`, zero `TODO`/`FIXME`, and zero `any` casts in app source.

### S3 — Small and cosmetic

- **No skip-to-content link.** Confirmed absent. With 1,050 focusable elements on the page, keyboard users tab through the entire nav before reaching content.
- **No `<h1>` on `/explore`.** Only one `<h2>` and one `<h3>`. Heading hierarchy starts at level 2 (SC 1.3.1 / 2.4.6).
- **`<footer>` landmark missing on `/explore`** (`footer: 0` in the landmark count) even though `Footer.tsx` exists — the Explore layout omits it.
- **Map container has no `aria-label`.** `#park-map` has only `id`, `class`, `tabindex="0"`. Leaflet makes it keyboard-operable by default (confirmed via context7's accessibility guide), but an unlabelled focusable region announces as a bare "group".
- **All 20 `<img>` are OSM tiles with `alt=""`.** Technically correct — decorative — but **none have `width`/`height` attributes and none carry `loading="lazy"`**. Tiles are inside a Leaflet-managed pane so this is largely moot, but the pattern is worth not repeating.
- **`maximum-scale=1` in the viewport meta** disables pinch-zoom on mobile, a WCAG 1.4.4 failure.
- **No meta description, no Open Graph / Twitter card tags.** `index.html` has a bare `<title>Park Pulse</title>` and nothing else — the site is unshareable and unindexable.
- **Google Fonts is render-blocking.** Inter is loaded via a `<link rel="stylesheet">` to `fonts.googleapis.com`. `font-display: swap` is set, so text shows, but the stylesheet itself blocks first paint. Self-hosting or preloading would remove a third-party dependency (also a privacy/GDPR consideration).
- **Decorative `·` separators in the modal render at 1.42:1 contrast.** Cosmetic only — `aria-hidden` would make that explicit.
- **`::root` used as a compound selector.** `index.css:834-837` writes `::root .pp-sidebar::-webkit-scrollbar`, which is invalid CSS; those four scrollbar rules never match. The `[data-theme=...]` scrollbar rules nearby *do* work, which is why the symptom is invisible.
- **Two live regions announce the same state.** `[aria-live=polite]` fires "6 parks visible" and, separately, the modal announces "1 / 95". Overlapping announcements are noisy for screen-reader users.

## 3. What is genuinely working well

Worth stating plainly, because it is a lot:

- **Zero long tasks** during map zoom and marker reconciliation. The `useCulledMarkerLayer` hook and view-bounds culling are doing their job.
- **157.3 kB gzip JS / 28.8 kB gzip CSS** — modest for a map app carrying Leaflet and 418 markers.
- **15.1 MB heap, 3,364 DOM nodes** with 2,023 locations loaded.
- **TTFB 6 ms, DOM interactive 38 ms, load 174 ms** (dev server; production will differ but the structure is sound).
- **Modal focus management is correct.** Verified: `Escape` closes, focus returns to `BUTTON | View details for Fitzroy Gardens`. This is the fix from the earlier phase, and it holds.
- **`prefers-reduced-motion` is honoured** with a correct global block (`animation-duration: 0.01ms !important`).
- **81 `:hover` rules, but cards also have `:focus`** with a `box-shadow` ring — the hover affordance is not the only path.
- **No `any` casts, no suppression comments, no `innerHTML`.**
- **`dataCache.ts` is exemplary** — real UTF-8 byte accounting (with a comment explaining exactly why `String.length` was wrong), per-entry ceilings, two-attempt quota retry, random eviction with a stated rationale, TTL, and a graceful private-browsing path.

**The app already ships fountains (273), toilets (3,127) and transport (1,164) and loads them correctly** via `useCulledMarkerLayer` — I initially suspected they were orphaned and that suspicion was wrong. Two provenance corrections to what I originally reported (full evidence in [AUDIT-2026-10-DEEP-RESEARCH.md](AUDIT-2026-10-DEEP-RESEARCH.md) §G): the toilets file is **not** a fork of the City of Sydney layer — it is an extract of the **Australian Government's National Public Toilet Map** (Dept. of Health, Disability and Ageing, CC-BY; 2,992 of its 3,127 rows join to the NPM CSV by name+coordinates, and its bbox spans all of Greater Sydney, which the 525-facility LGA layer cannot). The transport file is a **Transport for NSW GTFS `stops.txt` extract** (verbatim GTFS schema), complementary to — not a stale copy of — the 64-record CoS ArcGIS layer. The genuinely missing classes are **playgrounds (162), sports facilities (70), pools (6), libraries (11), recreation centres (6), seats (890), stairs (523), bridges (82), community gardens (22), venues for hire (37), bicycle parking (1,761)** — roughly **3,570 additional features**, a ~2.4× increase over the current 2,023.

Two schema findings that materially improve what the product can say:

- **The toilets layer is far richer than the flat array currently shipped.** The live layer carries `Accessible`, `AdultChange`, `BabyChange`, `AllGender`, `BabyCareRoom`, `DumpPoint`, `Shower`, `OpeningHours`, `KeyRequired`, `PaymentRequired`, `ChangingPlaces`, `Ambulant`, and sharps-disposal flags. The app's local `toilets-sydney.json` flattened all of that into `n/lat/lng/t/h/a/b` — a **data-lossy local fork** of a public dataset that is better than the original.
- **The sports layer has 22 boolean-ish sport columns** (AFL, Cricket, Rugby, Soccer, TennisCourts, Netball, Basketball, SkatePark, Pickleball, TableTennis, Hockey, Badminton, Futsal, Athletics, IndoorGym, OutdoorGym, Volleyball, Pool, CityPrograms). This supports a genuine "what sport can I actually play here?" feature that no competitor offers.

**Coverage beyond the LGA is the hard constraint.** City of Sydney covers only ~12% of greater Sydney by population. A systematic follow-up sweep of the CKAN portals (data.nsw.gov.au, data.gov.au) and ArcGIS Online org discovery **corrects what I originally reported here** — the full evidence is in [AUDIT-2026-10-DEEP-RESEARCH.md](AUDIT-2026-10-DEEP-RESEARCH.md) §D–§F. Summary:

- **Parramatta** (ArcGIS org `NrOjMi9LSYL3MUze`, owner `pcc2150`): playground equipment 144, drinking fountains 132, sporting fields 90, public toilets 62, BBQs 42, fitness equipment 41, picnic areas 29, hard-court surfaces 52, tennis courts 12, skate parks 3, trees 66,351 — genuinely rich and official.
- **Northern Beaches** (ArcGIS org `LRvZf9YQitIniyDH`): MTB trails 2,855 (11 layers), coast walks 501+250, toilets 179 (2 layers) — I previously reported "nothing usable"; that was wrong.
- **Hornsby** (ArcGIS org `VKqP0BP08pVXloHq`): crown reserves 1,418, walking tracks 232, library points 129, fire trails 887.
- **Woollahra** (org `zjbesynggtrdwb3p`): parks online map 294 (8 layers), open space & reserves 113. **Inner West** (org `dp2UIID5MUpTUFVA`): 359 Active Inner West. **Randwick**: 16 services incl. a leash-free-area geodatabase. **Bayside** (`cc24201a…`): parks & reserves 219, picnic tables 26, BBQ 6, playgrounds 4, public toilets 4.
- **Blacktown, Cumberland, Canterbury-Bankstown, Georges River, Sutherland** all have CKAN orgs on data.nsw.gov.au (22, 10, 27, 33, 28 packages respectively) — but every package is a **floodplain-risk study**, not facility data. Blacktown's only ArcGIS hit remains a personal account (`Phil.Woodbury_lpinsw`) with six capital-project points. **Newcastle** has Parks and Playground services (outside Sydney, useful as a template).
- City of Sydney also publishes on CKAN: the `city-of-sydney` org on data.nsw.gov.au holds **196 packages** including playgrounds, sports & recreation facilities, swimming pools, dog-off-leash parks, stairs, seats, fountains, recreation centres, libraries, bridges, community gardens, venues for hire and bicycle parking — every missing class above is available via a standard CKAN API, not only via ArcGIS REST.

**This is the central strategic finding, unchanged: there is no single authoritative source of Sydney's public facilities. Coverage is council-by-council, uneven, and in most LGAs facility-grade data is absent** (the only cross-LGA official datasets are the National Public Toilet Map — which is where the app's toilets file actually comes from — and the NPWS asset geodatabase). Any "all of Sydney" claim must either (a) scope honestly to the LGAs with real data, or (b) use OSM as the gap-filler — which is almost certainly where the existing `blacktown.geojson` came from, and which needs ODbL attribution and a stated accuracy caveat.

## 6. Research note — limitation (corrected 2026-10-06)

**This section as originally written is false, and is corrected here.** It claimed web search (`web_search`) returned `Hosted service tools are unavailable in a direct BYOK run` on every attempt. In the current environment `web_search` works, and the 2026 web-platform survey it promised is now done — see [AUDIT-2026-10-DEEP-RESEARCH.md](AUDIT-2026-10-DEEP-RESEARCH.md) §I. Headline results (web.dev, "New to the web platform in January", 2026-01-30): **CSS Anchor Positioning** and the **Navigation API** reached Baseline Newly available with Firefox 147 (anchor positioning is now supported in all major browsers); Chrome 144 added the **`<geolocation>` element**, the **Temporal API**, `::search-text` and `caret-shape`; Firefox 147 added SPA view-transition types. WCAG 2.2 is a W3C Proposed Recommendation, so the SC 2.5.8 touch-target findings in §2.5 are cited against a current standard.

The substitution I originally made — direct HTTP fetches against the ArcGIS REST APIs — did produce better evidence than a search would have (real item IDs, live feature counts, live field schemas), and that work stands. But the unavailability claim itself was an environment limitation of the earlier session, not a permanent constraint, and should not have been written as a general limitation of the research. PRD recommendations that rely on platform-capability assumptions should still be checked against the survey before adoption.
